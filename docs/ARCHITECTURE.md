# Architecture

Clio is a privacy-focused tool for indexing your own documents and data, chatting with them through a grounded, citation-first assistant, and exposing them to external agents over MCP. Think "NotebookLM for files you own" — the intelligence lives in whatever LLM you trust; Clio owns the trustworthy data layer in front of it.

> The `master` branch is this general-purpose tool. Domain-specific financial-analysis features (brokerage ingest profiles, portfolio metrics, market-data tools, meeting briefs) live on the **`fintech`** branch, which is a superset of `master`.

## Backend (Python / FastAPI)

- [main.py](../main.py) — thin app assembly: middleware, lifespan (initializes the embedding model, vector store, indexer manager, MCP server, and collection service), router includes, and frontend serving.
- [api/](../api/) — HTTP endpoints, one router module per domain: `documents`, `search`, `chat`, `artifacts`, `collections`, `mcp`, `sharing`, `expertise`, `system`. Shared helpers/state (e.g. `get_indexer`, the expertise store singleton) live in [api/deps.py](../api/deps.py). Routers carry their full URL paths — no prefixes — so the public API matches the module layout one-to-one. Business logic belongs in `services/`, not in routers.
- [config.py](../config.py) — pydantic-settings `Settings` loaded from `.env`. Defaults are the safe solo posture (loopback bind, no CORS); a Postgres backend is opt-in. `main.py` runs a startup check that refuses or warns on configurations promising more safety than the app delivers — see [DEPLOYMENT.md](DEPLOYMENT.md).
- [models/schemas.py](../models/schemas.py) — every Pydantic request/response model.
- [services/](../services/) — feature modules:
  - `services/indexing/` — `DocumentIndexer` (chunk → embed → write to vector store).
  - `services/document_extractor.py` — generic text/tabular extraction across PDF, DOCX, TXT, Markdown, CSV/XLSX, audio (transcription), with header-sniffing for messy spreadsheet preambles.
  - `services/code_extractor.py` — language-aware extraction for source files.
  - `services/structured_store.py` — `StructuredStore`, a typed SQLite table per ingested CSV/XLSX sheet. Domain-agnostic: custom types and column-role detectors can be layered on via `register_type_extension` / `register_role_detector`.
  - `services/structured_chat.py` — the provider-agnostic chat tool registry and dispatcher (see below).
  - `services/agent_tools.py` — the same tool registry rendered as native Anthropic / OpenAI tool schemas.
  - `services/mcp_server.py` — embedded HTTP MCP endpoint mounted at `/mcp`.
  - `services/expertise_store.py` — named, markdown-body "Expertise" packs: reusable research frameworks/instructions a user can attach to a collection.
  - `services/content_policy.py` — ingest-time content-policy scanner (local regex rule packs, optional LLM second opinion) and the clear/flagged/quarantined/rejected decision. `services/pii_detector.py` supplies its `pii` category (Presidio when installed, built-in regexes otherwise) and the optional output redaction.
  - `services/prompt_injection_detector.py` — the wording scan for text aimed at an AI reader: per-page verdicts at ingest, the document-level summary the review queue shows, admin tuning (muted rules, allowed wordings, reviewer feedback that turns noisy rules down; stored in the app database's config table) and `mark_passage`, which labels instruction-like passages wherever retrieval hands them out.
  - `services/governance.py` — sensitivity labels, quarantine/approve/remove, the hash blocklist, reports, user suspension, and the acceptable-use acknowledgement. `services/audit.py` is the append-only trail behind all of it.
- **Indexing jobs.** Anything that indexes more than one file is a background job in `services/upload_service.py`: a row in `upload_jobs`, a plan, and a thread the dispatcher hands out. `start_local_index` and `start_repo_index` never start a thread themselves — they call `_submit`, and `_dispatch` starts a job only when its collection has nothing running and the process is under `MAX_CONCURRENT_INDEX_JOBS`. Everything else waits in a FIFO queue and reports its place through `queue_position`, which is why a second submission for a busy collection is now accepted rather than refused with a 409; only a full waiting list (`MAX_QUEUED_JOBS`) is refused. `_run_job` owns the slot for the whole run, so a job that dies before its pipeline starts still frees its collection. Cancellation is cooperative and checked at two points — between files and before each embedding batch — because embedding a batch is the long pole and extraction routinely finishes first. Jobs do not survive the process that ran them, so `upload_service.recover_orphaned_jobs()` runs once in the lifespan and fails out every `pending`/`running` upload and re-index row; without it a restart mid-index left a job that read as running forever and a collection that refused all future jobs. A new bulk ingest path submits through the queue and reports through the same row; `GET /documents/jobs` is the history the UI reads, and per-file failures live in each job's `result_summary`.
- **Governance choke points.** Quarantined documents are filtered in `DocumentIndexer.search` (every retrieval surface), in the MCP document tools, and by `governance.assert_document_servable` on the pdf/chunks endpoints. Restricted collections are refused by `sharing_service.create_share` and by `mcp_server._resolve_collection_id` / `_visible_collections` unless the MCP token is scoped to them. The AUP gate lives in `api/documents._require_ingest` for the HTTP ingest paths and in `mcp_server._require_mcp_write` for agent writes. Every ingest path passes `uploaded_by` down to the indexer, which also hashes the file and consults the blocklist.
- **Collection-authority choke point.** `api/deps.require_collection_access` resolves one of three tiers and is the only place that decision is made. `owner` may change how a collection is built — re-index it, change chunking or embedding model, edit the guide or label, publish it, delete it. `readwrite` is a contributor: it adds and removes sources and nothing more, because re-indexing on an owner's behalf rewrites their index under them. `read` consumes. `sharing_service.check_collection_access` computes the tier and is where publication resolves to `read` for everyone but the owner, so the app, the collection list and every `/mcp` tool inherit it without their own branch. A new endpoint that reconfigures a collection passes `owner=True`; one that ingests passes `write=True`. Cloning (`collection_service.clone_collection`) is the deliberate escape hatch: read access is enough to take your own copy, which reuses the bulk upload pipeline and so inherits its quota accounting, auditing and progress reporting.
- **Identity choke point.** Clio has no accounts, no login page and no user store; by default requests are anonymous (an open appliance, optionally behind the `AUTH_PASSWORD` gate). `services/identity.py` is the only place a request becomes a *person*, and only for organisations that already run sign-in. One verifier per deployment, selected by `IDENTITY_PROVIDER` (empty by default): a bearer JWT from the site's own OIDC provider, or a header an authenticating reverse proxy vouched for. `services/admins.py` decides who is an administrator from `ADMIN_EMAILS`, which means something only when an identity provider supplies the identity. `PRIVATE_COLLECTIONS` refuses to start without one. `main.py`'s auth middleware calls `get_identity_verifier(path)` — which on the `/mcp` subtree also covers OAuth bearer tokens from the authorization server the endpoint advertises — and records the result on `request.state.auth_identity`; `middleware/user_context.py` carries it to service-layer code that has no `Request` in reach. `identity.validate_config()` runs in the startup posture check and refuses any configuration that cannot enforce what it claims — notably a trusted header with no guard, and OIDC with no audience. A new identity source is a new backend there, not a new branch in the middleware. See [IDENTITY.md](IDENTITY.md).
- [middleware/](../middleware/) — `user_context` resolves the owner recorded on collections. Multi-user mode is not supported (the app refuses to start with it enabled), so this resolves to `default_user_id` unless `PRIVATE_COLLECTIONS` is on; see [DEPLOYMENT.md](DEPLOYMENT.md) for why.

## Retrieval

`DocumentIndexer.search` is the one retrieval path (search, chat context, every MCP tool). Hybrid BM25 + vectors with the per-query balance from [services/retrieval_planner.py](../services/retrieval_planner.py), then the entity-graph and chunk-boost adjustments, quarantine filtering, and finally the local cross-encoder reranker ([services/reranker.py](../services/reranker.py)) over a wider candidate pool (`top_k × RERANKER_CANDIDATE_MULTIPLIER`, capped at 50). The reranker has two interchangeable backends for the same weights — fastembed (the ONNX export on onnxruntime, no PyTorch; the default, baked into the Docker image next to the embedding model) and sentence-transformers — resolved by `reranker.resolve_backend`. `ENABLE_RERANKER` unset means on whenever the model is on disk; the startup warm-up fetches it once when downloads are allowed (`reranker.warm_in_background`, never under `OFFLINE_MODE`). Pairs are scored in length-sorted batches so padding is not paid for by short passages, at most `RERANK_MAX_CONCURRENT` passes run at once, and a search that cannot get a slot within `RERANK_QUEUE_TIMEOUT_SECONDS` answers in retrieval order with `retrieval.reranked: false` — bounded latency under a burst of agent calls is the contract. `reranker.status()` is what readiness and the MCP `health_check` report.

Spreadsheets are the exception to "one retrieval path": CSV/XLSX are typed SQL tables only, never chunked or embedded, so that totals and rankings are computed rather than guessed from passages. So that their rows are findable without a model, `POST /search` (the Find tab) adds exact row matches from [services/table_row_search.py](../services/table_row_search.py): `StructuredStore.find_rows` returns rows holding every keyword of the query (a term naming the table — a header, the filename, the sheet — counts as present), filtered by quarantine and the request's `filters`, and `merge` puts them ahead of the passages in at most half the list. An explicit `semantic` search skips them. Chat and the MCP tools are unchanged: they reach tables through the table tools. [scripts/retrieval_bench.py](../scripts/retrieval_bench.py) measures this whole path against the versioned fixture corpus in [tests/fixtures/retrieval_bench/](../tests/fixtures/retrieval_bench/) (recall@k, MRR, latency, shedding per reranker configuration); its numbers justify the pool and concurrency defaults in `config.py`.

## Chat

Chat is one pipeline, `api/chat._run_turn`: answer cache → provider → retrieval → prompt → agent loop → follow-ups → usage, written as a synchronous generator of events (`tool_start`, `tool_end`, `thinking`, `text`, `sources`, `related`, `done`, `error`). `POST /api/chat` drains it into a `ChatResponse` (the Generate tab reuses this); `POST /api/chat/stream` relays each event as SSE from a worker thread. There is deliberately no second copy of the loop.

- Providers with native tool calling (Anthropic, OpenAI family) get the JSON-Schema tools from [services/agent_tools.py](../services/agent_tools.py). Ollama gets the prose protocol from `build_tool_use_instructions` and its `<tool_call>{...}</tool_call>` blocks are parsed out of the reply. Both paths dispatch through `execute_tool_calls` in [services/structured_chat.py](../services/structured_chat.py), which runs the in-process MCP tool functions against the per-collection `StructuredStore` and document index and feeds the results back on the next pass. A turn that hits the iteration cap gets one final no-tools pass so it always ends in an answer.
- **Source selection** (`ChatRequest.document_ids`) is enforced in `execute_tool_calls` by `_SourceSelection`: search filters are intersected with the selection, document reads and table tools are refused outside it, and the collection is pinned — a `collection_id` the model passes is ignored, because models copy the collection's name from the overview and a refusal only makes them retry until the turn fails.
- The tool registry: `search_documents`, `get_document_context`, `list_tables`, `get_table_schema`, `get_table_rows`, `query_table`, `aggregate_table`, `list_collections`, `get_collection_info`. The in-app chat and the MCP endpoint expose the same primitives.
- The system prompt frames the assistant as a research assistant that grounds every claim in the provided sources, cites them, and says so plainly when the sources don't contain the answer.
- **Answer depth** (`ChatRequest.depth`). `quick` answers in one provider pass from the retrieved passages and inlined tables: no document-research tools, so time-to-answer is one round-trip; the table tools stay available only when large tables exist behind them. `research` (the API default) is the full agent loop with `research_documents` / `find_in_documents` / `get_document_context`. The UI defaults to Quick and offers "Go deeper" on any quick answer. Depth is part of the answer-cache fingerprint. Helpers: `api/chat._tools_for_depth`, `_depth_instructions`.
- **Answer cache** ([services/answer_cache.py](../services/answer_cache.py), chat-layer helpers in `api/chat.py`). Single-turn questions are embedded with the local model and matched against answers already generated under the same scope key. The similarity floor is per request: `ChatRequest.cache_threshold` (the Chat Settings "Reuse cached answers" slider, seeded from `GET /api/chat/cache`) falls back to `ANSWER_CACHE_THRESHOLD`. Similarity is only a candidate lookup — `_same_question` accepts a rephrasing but refuses questions whose numbers or negations differ, and at threshold 1.0 only the identical text counts. Cited sources are re-fingerprinted on every hit, so an edited or vanished document discards the entry; `cached_similarity` on the response/`done` event shows how close the match was.
- **Suggested questions** ([services/chat_followups.py](../services/chat_followups.py)). After an answer settles, one fast-model call proposes up to three follow-ups (`related` SSE event, `related_questions` on the response and on the `done` event; stored with the cached answer in `answer_cache.related_json`). `POST /api/chat/starters` writes opening questions from the collection overview plus the first passage of a few servable documents, cached in-process per `(collection, corpus_version, selection, provider, model)`. Both are best effort: a provider or parsing failure yields an empty list, never a failed turn. Document text is passed as evidence and parsed defensively; it is never treated as instructions.
- **Provider choke point.** Every AI surface — chat, artifacts, vision OCR, schema inference, the content-policy reviewer, connection tests — builds its provider through `ai_service.create_provider`, and nothing else constructs one. Two deployment-wide rules live there: `OFFLINE_MODE` refuses anything but `ollama` / `openai_compatible`, and `apply_deployment_defaults` fills in the endpoint, model and key an operator configured (`AI_PROVIDER` / `AI_BASE_URL` / `AI_MODEL` / `AI_API_KEY`) for values the caller left empty. That is what makes an on-prem install work against a private model with no per-browser setup, while a caller that brings its own key still overrides it. Credentials resolve through `deps.resolve_ai_key` (header → stored team key → deployment default); `GET /api/ai/deployment` tells the frontend what to offer, and never returns the key. See [ONPREM.md](ONPREM.md).

## MCP

The embedded MCP server ([services/mcp_server.py](../services/mcp_server.py)) is mounted at `/mcp` for power users who already work inside an external MCP client.

The in-app chat is the primary surface; the MCP endpoint is secondary.

- **Reading** — the same retrieval primitives as chat (`search_collection`, `search_all_collections`, `find_in_documents`, `get_document_context`, the table tools) plus orientation tools and `collection://` / `document://` / `table://` resources.
- **Answering** — `ask_documents` is a thin adapter over `api/chat._run_turn` (`mcp_server.ask_documents_sync`): the same retrieval, reranking, inlined tables, answer cache and usage accounting as the in-app chat, returned as `answer` + numbered `sources` in one call. It takes a research slot and runs on the deployment's own model (`AI_PROVIDER`), so it is registered only when one is configured — `_ASK_AVAILABLE` also decides whether the server instructions mention it. An MCP call carries no per-user key, which is why there is no bring-your-own-key variant.
- **Transports** — streamable HTTP at `/mcp` (stateless, JSON responses; `main._MCPPathNormalizer` serves the bare path without a redirect) is the recommended and default shape. `mcp_server._with_legacy_sse` adds the 2024-11-05 HTTP+SSE transport beside it (`GET /mcp/sse`, `POST /mcp/sse/messages/`) for clients that offer nothing newer; it shares the server, the auth middleware, the `?collection_id` profile and the DNS-rebinding settings, and keeps one in-memory session per open stream. The Connect tab's recipes live in `frontend/src/utils/mcpClients.js`, one entry per client, grouped; the server never sees a snippet.
- **Never on the event loop** — FastMCP calls a plain `def` tool inline on the event loop, so one slow SQL query would have stalled every other client. Every synchronous tool and resource is registered through `_threaded_tool` / `_threaded_resource` (`_offloaded`): FastMCP gets an `async` wrapper that runs the function with `asyncio.to_thread` (context variables — token scope, identity, profile — copied into the worker), while the module keeps the original synchronous function for in-process callers such as the chat tool executor and the tests. `functools.wraps` keeps the derived schema identical. Both thread pools (asyncio's default executor and anyio's limiter) are sized to `WORKER_THREADS` at startup (`main._size_worker_pools`), and `scripts/mcp_load.py` measures the result.
- **Writing** — `write_document(filename, content, collection_id, mode)` lets an agent add a text source (markdown, txt, json, csv, html, code) to a collection or update one it added before (`create` / `replace` / `append`). It stores the file in the collection's documents directory and runs the normal indexing pipeline, so the content policy scan, attribution (`uploaded_by`), and the audit trail all apply. Every write goes through `mcp_server._require_mcp_write`: collection visibility (`_resolve_collection_id`), the token's write flag, the collection's write permission under private collections, and the AUP gate. There is deliberately no delete tool.
- **Token write flag** — personal MCP tokens are read-only unless minted with *Allow adding and updating sources* (`can_write` on the `mcp_tokens` row). The auth middleware records it on `request.state.mcp_token_can_write`; `ToggleableMCPApp` binds it to a contextvar the write tool consults. Callers that are not personal tokens (an SSO session, `AUTH_PASSWORD`, the in-process chat loop) are full users and may write, subject to the same collection and policy gates.
- **Audit choke point** — `_tool_response` is the single seam every tool result passes through, which is where `MCP_AUDIT_TOOL_CALLS` records an `mcp.tool_call` event: the tool, the verified identity, the token id, the collection, the documents touched and the result counts. Metadata only — never passage text, because the audit table is read by more people and kept longer than the corpus it describes. Off by default; required for deployments that must answer "which credential read which document, when". A new tool gets auditing for free by returning through that seam.
- **Authored text is data** — collection guides, names, descriptions and Expertise packs are written by people and delivered to other people's agents, which is the ContextCrush shape. `services/authored_text.py` scans them on save (stored verdict, never a block), wraps prompt text in delimited provenance blocks, and adds `guide_provenance` / `authored_text_note` beside the plain strings in MCP responses. Pack writes are admin-only and audited; attaching packs and editing the guide are owner-only and audited. Every channel, author and mitigation is listed in [SECURITY_AUTHORED_TEXT.md](SECURITY_AUTHORED_TEXT.md).
- **Authentication shapes** — clients that send a static bearer header (Claude Code, Codex, VS Code, AnythingLLM) attach with a personal token; the config for each is generated in Settings → MCP. Connector-style clients (Claude Desktop, claude.ai, ChatGPT, and Claude Code without a token) speak the MCP authorization spec, and the app implements exactly the resource-server half of it: RFC 9728 protected-resource metadata at `/.well-known/oauth-protected-resource[/mcp]` and a `WWW-Authenticate: Bearer resource_metadata="…"` challenge on the `/mcp` 401 ([services/mcp_oauth.py](../services/mcp_oauth.py), routes in `api/mcp.py`), naming the site's IdP as the authorization server. There is deliberately no embedded authorization server and no client registry: sign-in, consent and client registration are the IdP's, and the bearer token that comes back is verified by the same `OIDCIdentity` a browser session uses — `get_identity_verifier(path)` hands the `/mcp` subtree a verifier whose accepted audiences add the canonical resource URL (`MCP_PUBLIC_URL`, RFC 8707) and which enforces `MCP_OAUTH_SCOPE` with the spec's 403 `insufficient_scope`. So an OAuth caller *is* the person, and private-collection scoping and the audit `actor` follow with no MCP-specific code. See [IDENTITY.md](IDENTITY.md#oauth-for-mcp-clients).

## Research workspace

[services/research/](../services/research/) layers a paper library over an ordinary collection; `api/research.py` is its router and `ResearchTab.vue` its view (the map, `ResearchMap.vue`, is an Obsidian-style canvas force graph — `force-graph` over d3-force — whose model and settings live in `utils/citationGraph.js`; it is loaded only when opened). The view's scope is the app-wide source selection (`selectionStore`), passed as `document_ids` to analysis, screening, renaming, reviews and the graph. See [RESEARCH.md](RESEARCH.md).

- **No model writes metadata.** `extract.py` reads title, authors, year, DOI/arXiv id, abstract, reference entries and body links from the paper's re-extracted page text (`library.paper_pages`, falling back to chunks), every field with a provenance entry. Books (an ISBN, or 80+ pages) are read differently: title page after a cover, copyright-page year, ISBN, an *opening* (preface/introduction, labelled as such) when there is no abstract, and every chapter's reference list. `lookup.py` consults OpenAlex / Crossref / arXiv / Open Library only for identifiers printed in the source, and `library._confirm_registry` discards a record whose title is not printed where the source's own title is (page one, or a book's front matter); a reference title search must find its title printed in the reference (`grounding.similarity`). `OFFLINE_MODE` / `RESEARCH_LOOKUP_ENABLED` turn lookups into no-ops.
- **Every model statement is verified.** `relevance.py` (worth my time?) and `briefs.py` (reviews) show the model numbered chunks (`passages.py`) and require `{point, quote, passage}` items; `grounding.verify_statements` keeps an item only if its quote is found in a passage the model was shown, tolerating extraction noise but never a changed number or negation (`grounding.faithful`). Dropped items are counted on the result. Thorough reviews merge windows deterministically instead of with another model call.
- **Storage.** `store.py` keeps `research_*` tables inside the collection's `metadata.db`, so export/import and backups carry them; readers ignore rows for deleted documents and `prune_orphans` sweeps them. Renaming (`naming.rename_document`) moves the stored file (never a local reference's), updates `documents` and `chunks` via `MetadataStore.rename_document`, records the original name once, and clears the collection's answer cache.
- **Background jobs.** `jobs.py` runs analyze/assess/brief batches on a thread with a process-wide slot limit (`RESEARCH_MAX_CONCURRENT_JOBS`), an optional `not_before`, cooperative cancellation, the daily token budget checked per paper, and the provider (built from the submitting request) held only in memory. Jobs the process no longer knows are reported failed on the next listing.
- **Downloads** go through `upload_service.start_link_index`, i.e. the same validated, SSRF-guarded link fetcher, AUP gate and audit trail as *Add link*.

## Frontend (Vue 3 + Vite)

- [frontend/src/App.vue](../frontend/src/App.vue) — the shell: a ribbon of icons down the left edge (`AppRibbon.vue`) with every destination and the everyday actions, grouped by purpose (asking, working with sources, sharing, actions) with a divider between groups, then the Sources panel, the main surface, and the Studio sidebar (right). The ribbon is customizable — Settings → Layout, the right-click menu, or *Customize the ribbon* in the command palette — to hide, show and reorder items or show names beside the icons, and icons can be dragged on the ribbon itself; the layout is a per-browser preference (`utils/ribbon.js`, `stores/layoutStore.js`, `clio_ribbon` in localStorage) that new items join with their default visibility. The Sources panel is shown wherever the source selection scopes the work (Ask, Find, Research, Reports) and lists sources as a folder tree by default (`SourcesTree.vue`, `utils/sourceTree.js`): synced folders and git repositories keep their sub-folders and each file's own name, links group by site, uploads sit at the top level; every row keeps the governance markers of the detailed list (held/flagged, prompt-injection note, sensitivity label, replaced); checking a folder selects everything in it, right-click offers the file actions, and the detailed list remains a toolbar toggle away. Because a tree is only right when it holds the whole collection, folder view loads every page (in steps of 1,000, up to 10,000 sources, and says so beyond that), and a large tree opens one level deep. Per-tab components in [frontend/src/components/](../frontend/src/components/) (ChatTab, SearchTab, ArtifactsTab, ResearchTab, ExpertiseLibrary, MCPTab, SettingsTab, …).
- **Responsive shell.** Three layouts from one template: desktop (≥1024px) has the ribbon and inline, resizable side panels; tablet width (768–1023px) keeps the ribbon and the panels inline but only one open at a time; phones (<768px) replace the ribbon with a bottom tab bar, fold Settings/Help/provider/account into one overflow menu, hide the status footer (an active-job spinner takes its place in the header), and open the side panels as full-width sheets. Hover-revealed row actions use the `.hover-reveal` utility in `style.css` so they are always visible on touch screens; xs icon buttons grow on coarse pointers; phone widths get a 16px floor on form fields so iOS does not zoom.
- Pinia stores in [frontend/src/stores/](../frontend/src/stores/).
- The Vite dev server runs at `:5173` and proxies to the backend at `:8473`. The production build lands in `frontend/dist/` (gitignored) and is served by FastAPI with long-lived immutable caching for hashed `/assets/*` files; Docker images build it in a dedicated node stage.

## Design language

The UI follows the principles in [.impeccable.md](../.impeccable.md): the document is the subject, the app is the room. NotebookLM as reference, generic SaaS dashboard as anti-reference. Components stay theme-agnostic — use DaisyUI semantic tokens, never hard-coded colors. The name, the Muse's symbols and how they map onto the product are in [BRAND.md](BRAND.md).
